Why a language model remembers instead of re-reading

Generating text is a loop that asks the same question again and again. The KV cache is the trick that stops the model from redoing work it already did, and it decides how many users one GPU can serve.

1. The generation loop

A language model is a function. You give it a list of tokens (pieces of words, each mapped to an integer) and it returns a probability for every token in its vocabulary: how likely each one is to come next.

To write a sentence, you call that function, pick a token, append it to the list, and call the function again with the longer list. That's all text generation is. Step through it:

2. What attention needs from the past

Inside the model, the part that lets a token use earlier tokens is attention. In every layer, each token is turned into three vectors by multiplying it with three learned weight matrices:

q = x · W_Q "what am I looking for?" (query) k = x · W_K "what do I contain?" (key) v = x · W_V "what do I hand over?" (value)

The newest token compares its query with the key of every earlier token. A dot product measures how well they match. Softmax turns those scores into weights that sum to 1, and the output is the weighted sum of the earlier tokens' values:

score_i = q_new · k_i / √d for every earlier token i weight_i = softmax(score)_i output = Σ weight_i · v_i

The crucial detail: a token may only look backwards (the causal mask). Token 3 never sees token 7. So once token 3's key and value are computed, nothing that happens later can change them.

4. Cache it

Because past keys and values never change, store them. Each call then does three things for the new token only: compute its q, k, v, append k and v to the cache, and attend over the whole cache. That stored list of keys and values, one pair per token, per layer, is the KV cache.

Queries are not cached: only the newest token's query is ever used, and it's thrown away after its step.

for each layer: q, k, v = x_new @ W_Q, x_new @ W_K, x_new @ W_V K_cache.append(k); V_cache.append(v) out = softmax(q @ K_cache.T / sqrt(d)) @ V_cache

This is the same code you'll read in platform/engine/v0/reference/llama_numpy.py, where self.k_cache[l, pos] = k is the append.

5. Prefill and decode: two very different jobs

With a cache, a request runs in two phases. Prefill processes the whole prompt in one forward pass: all prompt tokens go through each weight matrix together, as one big matrix–matrix multiply, and the pass fills the cache and produces the first output token. Decode then produces one token per pass.

Here is why they behave differently. Every pass must read all the model's weights from GPU memory. In prefill, each weight read is reused for hundreds or thousands of tokens, so the GPU spends its time computing: compute-bound. In decode, each weight read serves a single token, so the GPU spends its time waiting for memory: memory-bound.

6. How big is the cache?

Every token stores one key and one value vector, in every layer, for every key/value head. So the size per token is a product of five numbers you can read straight from a model's config.json:

bytes per token = 2 (K and V) × layers × kv_heads × head_dim × bytes per number

For Llama-3-8B (32 layers, 8 KV heads, head dimension 128, bf16 = 2 bytes) that is 2 × 32 × 8 × 128 × 2 = 131,072 bytes: 128 KiB for every token. A single 8,192-token conversation needs 1 GiB of cache. Try other models and settings:

Check yourself

Why are queries not stored in the cache?

Each query is used once, by the token that made it, in its own step. Later tokens attend with their own queries against old keys and values.

Generating 1,000 tokens without a cache: roughly how many K,V computations per layer?

1 + 2 + … + 1000 ≈ 500,500, against 1,000 with a cache: about 500× more.

Your model uses 8 KV heads instead of 32 query heads. What does that do to the cache?

It shrinks it 4×. That's grouped-query attention (GQA): several query heads share one key/value head.

Why is decode memory-bound even on a very fast GPU?

Each decode pass reads all the weights to produce one token per sequence, so it does about 2 FLOPs per weight byte read. That is far below what any GPU needs to keep its compute units busy. Batching several users into one pass is how servers raise it.
