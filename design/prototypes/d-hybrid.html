The model that refused to read twice

Scroll. The panel on the right is a tiny language model. Every step changes it, from the generation loop to the memory bill that decides how many people one GPU can serve. Four checkpoints along the way test what you just saw.

STEP 1 · THE LOOP

Generation is a loop

A language model is a function. Give it a list of tokens (word pieces, each an integer) and it returns a probability for every possible next token.

To write text, pick a token, append it, and call the model again with the longer list. Five new words means five calls, and each call sees all tokens so far.

STEP 2 · Q, K, V

Every token makes a key and a value

Inside each attention layer, every token vector x is multiplied by learned weight matrices:

k = x · W_K what I contain (key) v = x · W_V what I hand over (value) q = x · W_Q what I'm looking for (query, newest token)
STEP 3 · ATTENTION

The new token looks back

The query is compared with every earlier key by a dot product. Softmax turns the scores into weights that sum to 1 (line thickness). The output is the weighted sum of the values.

out = Σᵢ softmax(q · kᵢ / √d) · vᵢ

A token can only look backwards (the causal mask). So an old token's key and value can never change.

STEP 4 · THE WASTE

Without memory, everything is recomputed

A naive loop forgets between calls. Call t rebuilds all t keys and values, in every layer. The red chips are identical numbers computed again.

Over n tokens that's 1 + 2 + … + n ≈ n²/2 computations when only n are new.

STEP 5 · THE CACHE

Keep them: the KV cache

Store each key and value the first time it's computed. Each call now computes one new pair, appends it, and reads the rest:

K_cache.append(x_new @ W_K) V_cache.append(x_new @ W_V) out = softmax(q @ K_cache.T / √d) @ V_cache

Queries aren't cached: each is used once, by its own token. This is exactly self.k_cache[l, pos] = k in the repo's llama_numpy.py.

STEP 6 · PREFILL

Prefill: the whole prompt at once

The prompt is known up front, so all its tokens go through the model in one pass. Each weight read from memory is reused by every prompt token, so the GPU spends its time computing: compute-bound.

This pass fills the cache and ends with the first output token. Its length is the time to first token (TTFT).

STEP 7 · DECODE

Decode: one token per pass

After prefill, each pass produces one token per user. It still reads all the weights, plus the cache, for a single token's worth of math: about 2 FLOPs per byte read. The GPU mostly waits on memory: memory-bound.

The gap between tokens is the inter-token latency (ITL). Batching users into one pass makes each weight read serve more tokens.

STEP 8 · THE BILL

The memory bill

One key and one value per token, per layer, per KV head:

bytes/token = 2 × layers × kv_heads × head_dim × bytes Llama-3-8B, bf16 = 2 × 32 × 8 × 128 × 2 = 131,072 B = 128 KiB

An 8k-token conversation needs 1 GiB. With 16 GB of weights on a 24 GB GPU, only seven such users fit. Memory, not compute, sets the limit.
